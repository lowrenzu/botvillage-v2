## 1. Points forts

- **Posture sécurité réfléchie et cohérente avec le README** : écoute loopback par défaut, comparaison de jeton en temps constant (`subtle.ConstantTimeCompare`), cookie de session **opaque** HttpOnly (jamais le secret brut), jeton HUD en mémoire seulement (vérifié dans `sim.ts`, avec `localStorage.removeItem` de migration), fichiers secrets en 0600, `wakes.jsonl` ne garde que `promptLen` (jamais le texte du prompt).
- **Validation des entrées** : `MaxBytesReader` (4 ko), limite prompt 2 000, `SanitizeID` exige la forme UUID (traversée de chemin impossible — testé), `Exists()` avant tout POST webhook, rate-limit 12/min/IP sur `/api/prompt` et `/api/session`.
- **Docker correct** : multi-stage, utilisateur non-root (uid 10001), aucun secret dans l'image, volume agent-data en `:ro`, publication hôte limitée à `127.0.0.1`.
- **`/ws`** : allowlist d'Origin + same-host, testée.
- Écriture atomique de `.village-sessions` (temp + rename, 0600), purge des sessions expirées au chargement et à l'écriture.
- Arrêt propre (`signal.NotifyContext` + `Shutdown` 3 s).

## 2. Risques sécurité

### S1 — Reverse proxy local = bypass d'authentification total (élevé si exposé)
`localRequest()` ne regarde que `RemoteAddr`. Tout reverse proxy sur la même machine (nginx, caddy, `tailscale serve`…) qui forwarde vers `127.0.0.1:8040` fait apparaître **tout le trafic distant comme loopback** → plus aucun jeton demandé, `/api/prompt` ouvert au monde. `X-Forwarded-For` n'est ni lu (ce qui est sain par défaut) ni documenté comme piège. Même effet secondaire sur le rate-limit : derrière un proxy, toutes les requêtes partagent le même seau IP.
**Reco** : avertir explicitement dans le README (« ne mets jamais un reverse proxy devant sans `VILLAGE_PROMPT_TOKEN` + un flag type `VILLAGE_TRUST_PROXY` »), et/ou option opt-in de confiance aux en-têtes forwarded.

### S2 — Routage Grok Build par **nom** d'agent (moyen)
`isGrokBuildTarget()` route vers `api.x.ai` si le nom de l'agent est « grok », « Grok Build » ou *contient* « grok build ». Un agent quelconque renommé ainsi dans `profile.json` voit ses prompts partir chez un tiers (xAI) au lieu du webhook Cursor — exfiltration silencieuse par simple renommage. L'UUID `da2f664d-…` codé en dur dans un dépôt public est aussi un identifiant propre à une install (couplage + fuite d'info mineure).
**Reco** : ne router que sur `target: "grok-build"` explicite (déjà supporté) ; sortir l'UUID vers une env `VILLAGE_GROKBUILD_ID`.

### S3 — `VILLAGE_LOCAL=1` par défaut dans `docker-compose.yml` (moyen)
Le compose publie certes `127.0.0.1:8040`, mais le commentaire invite à retirer le `127.0.0.1` pour Tailscale — avec `VILLAGE_LOCAL=1` déjà posé, l'install devient alors ouverte à tout le LAN sans jeton, en une seule édition. Le check se fait de plus via `os.Getenv` à **chaque requête** (coût mineur, mais surtout non figé au démarrage).
**Reco** : ne pas pré-activer `VILLAGE_LOCAL` dans le compose ; lire l'env une fois au boot.

### S4 — Rate-limiter non borné (faible)
`promptLimiter.hits` n'évince jamais les IP inactives → croissance mémoire lente sous churn d'IP (IPv6). Et `allow()` est consommé **avant** `authorized()` sur `/api/prompt` : des requêtes non authentifiées épuisent le quota des utilisateurs légitimes derrière le même NAT.
**Reco** : purge périodique de la map ; compter le hit seulement après auth réussie (ou seaux séparés).

### S5 — En-têtes de réponse (faible)
Pas de `Content-Security-Policy` ni `X-Frame-Options`/`frame-ancestors` sur `/` → clickjacking possible sur une install exposée. (`nosniff` et `Referrer-Policy` sont déjà posés, bien.) Le single-file inline rend une CSP stricte difficile, mais `frame-ancestors 'none'` est posable sans rien casser.

### S6 — Divers (faible)
- `origin.go` : un Origin de **même hostname mais port différent** est accepté (coupure du port avant comparaison). Risque faible mais élargissement inutile.
- `truncate()` de `main.go` coupe en **octets** → peut produire de l'UTF-8 invalide dans `detail` (contrairement à `appendGrokLine` qui coupe en runes). À unifier.

## 4. Qualité de code

- `main.go` (760 lignes) cumule routes, sessions, limiter, auth — un découpage `internal/server` + `internal/session` rendrait ça testable sans l'état global (`sessionOK`, `sessionMu` au niveau paquet).
- Code mort : `redactPrompt()` (webhook.go) jamais appelée ; `hostPort`/`splitHost` doublon trivial dans main.go.
- `webhook.Client.Post` relit `webhook.json` à chaque envoi — OK pour la rotation de clé, mais non documenté comme intentionnel.
- Couverture faible sur les chemins d'erreur réseau (`webhook` 23 %, `grokbuild` 26 %) et sur les handlers de `main.go` (47 %) — ce sont précisément les chemins sécurité (`authorized`, gate, sessions) qu'on voudrait blindés.
- 2 fichiers hors `gofmt` (voir tableau) — correction en 10 secondes, ajouter un check CI.
